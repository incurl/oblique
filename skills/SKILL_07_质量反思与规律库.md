# SKILL 07: 质量反思与规律库

> **核心理念**：**完成不等于正确。**
> 三次自我否决都发生在"看起来已经能用"的时候。

---

## 一、任务定义

### 1.1 何时使用

- 一轮标注跑完，要评估质量
- 发现一类新的错误
- 交接给别人之前

### 1.2 输入与产出

| | 内容 |
|---|---|
| 输入 | 当前标注结果 + 领域指标 |
| 产出 | 修正后的数据 + **新增规律条目** |
| 前置 | [SKILL_05](SKILL_05_形制校验.md) |
| 后继 | 下一轮 |

### 1.3 成功标准

- [ ] 领域指标朝预期方向变化
- [ ] 发现的错误模式**已固化为规律**（不只改了这一处）
- [ ] 规律库条目可被下一个 Agent 直接使用

## 二、反思的三个动作

### 2.1 动作一：把隐式判断显式化

例：判断 `万安` 该不该标成地名。

**不要直接改词表，先列出所有可疑词及其语境**：

```
万安 | 瑞启万安殿外，矞云垂北极          ← 殿名
万安 | 成化戊戌，庶常安徽倪进贤，出入万安之门  ← 人名（明代宦官）
万安 | 第一滩在万安县                  ← 县名 ✅
```

三处语境，三种含义。**只要有一处是普通词，就该进黑名单。**

Agent 做这件事比人快：一次扫描 2,289 段，把同类问题聚成一堆。

### 2.2 动作二：把一次性修正固化为规则

发现问题后，不是只改这一处，而是问**"还有多少同类"**：

```python
# 发现 1 处误标 → 找出所有可能同形的词
AMBIGUOUS_PLACES = set("""
余庆 安定 永宁 … 万安 云霄 汾阳 仁寿 新建 华亭 紫阳 龙门 建阳 无为
""".split())
```

### 2.3 动作三：构造可复算的校验

把"我检查过了"变成"脚本检查过了"：

```bash
python3 scripts/lint_text_integrity.py
```

## 三、什么时候该怀疑数据

**依据不是"看起来对不对"，而是"统计上合理吗"。**

| 信号 | 阈值 | 说明 |
|---|---|---|
| 上下联等长率 | < 90% | 楹联基本形制，低于此必有切分错误 |
| 某类型标注数异常暴涨 | 加 1 词后涨 > 50 | 该词是高频普通词 |
| 某实体排名反常 | 如作者榜出现"庄子" | 误判（集句的被集诗人） |
| "联语"兜底类占比 | > 25% | 类型规则需要补 |
| 段落数 | 与源文件缩进行数不符 | 续行处理有问题 |

> **不合理的地方，是数据自己喊出来的。**
> 等长率 1.4%、作者榜出现"庄子"——这两次都是数据先叫的。

## 四、Y 规律库

> 每条规律都来自一次真实的错误。
> **改动前先读这一节**，能省下大量返工。

### 4.1 底本与符号（Y0）

| 编号 | 规律 | 来源 |
|---|---|---|
| **Y0** | 电子本目录（4–78 行）不是原文，排除后由结构树重建 | 分层判断 |

### 4.2 词表与同形词（Y1–Y4）

| 编号 | 规律 | 来源 |
|---|---|---|
| **Y1** | 与普通词同形的专名**不收入地名表**，进 `AMBIGUOUS_PLACES` | 万安、云霄、仁寿等 30 余例 |
| **Y2** | 朝代单字只在其后接「代/朝/室/末/初/世/人/以来」时标注；周/夏/虞/商 更严，只认「代/朝/室」 | 「周室」标对，但「周览」「夏云」误标 |
| **Y3** | 「聪明人」不是明朝人 | 单字朝代需加例外：`if 明 and 前一字=='聪': skip` |
| **Y4** | 典籍只标《》内部，书名号保留在标记外 | 边界原则 2 |

### 4.3 联语切分（Y5–Y7）

| 编号 | 规律 | 来源 |
|---|---|---|
| **Y5** | 联句末尾句读不属于联句本身 | 等长率 1.4% → 93.7% |
| **Y5b** | 集句联的**出处冠名**不属于联句本身（四种位置：下联前后、上联前后） | 93.7% → 99.34% |
| **Y5c** | 夹注/异文/议论按语/脱文/叙述误收等九类混入须**逐例人工判定** | 99.34% → **100%** |
| **Y6** | 联语作者必须"人名 + 撰/题/书联/作联/集句"紧接 | 覆盖率 8.4%→3.0% 但可用 |
| **Y7** | 「七十对联」中「对」不是数量单位 | 数量正则加负向断言 `对(?!联)` |

### 4.4 编者标记（Y8–Y10）

| 编号 | 规律 | 来源 |
|---|---|---|
| **Y8** | 「见上」「一作」「又作」是编者标记，剥离后记入 `editorial_markers` | 28 → 20 副 |
| **Y9** | 出处识别靠**形制自证**（剥离后等长），词典只用于确认 | 纯词典枚举必漏 |
| **Y10** | ⚠️ **「一曰」不是编者标记**——它是五行名目的正文 | 误加后破坏「以生一曰水」，已回退 |

### 4.5 Y10 的价值

Y10 是唯一一条"反向"规律——它记录的是**我自己犯的错**：

```
❌ 曾把 EDITORIAL_MARKERS 设为 ("见上","一作","又作","一曰")
   → 破坏「受天地之中，以生一曰水」
✅ 回退为 ("见上","一作","又作")
```

**教训**：**"看起来像"的字眼必须逐个查证，不能批量处理。**

> 这与 Y1 同源：都是"词形相同、语义不同"。
> Y1 讲词表，Y10 讲行内标记，本质是同一个陷阱的两种形态。

## 五、三次自我否决

规律库记"该怎么做"，这一节记"**曾经做错什么**"。
失败的设计比成功的更值得记住。

### 5.1 第一次否决：把联语包进实体层

**想法**：既然 `〖TYPE 内容〗` 能装人名，为什么不能装联语？

```markdown
〖聯 慧眼光中，开半亩红莲碧沼；烟花象外，坐一堂白月清风〗
```

**为什么看起来合理**：语法统一、位置明确、渲染简单。

**为什么失败**：联内"林少穆"**无法标注**。
标记已占满整个区间，实体只能落在外面或里面——两者都违反不嵌套。

**留下的启发**：

> **标记的形状决定了它能标注什么。**
> 包裹式标记只能标"叶子"，无法标"含有叶子的枝干"。

### 5.2 第二次否决：移植动词层

**想法**：`⟦◈⟧` 本来就是为"动作"设计的，联语也是一种动作（题、书、悬）。

**为什么失败**：

1. 动词层是**单字动词**词表（伐/攻/杀/诛/立/封），
   而联话的动作是复合的："题联""书楹""集句"——一个都不在表里
2. 动词层有强烈**史料偏向**，42 个词几乎全是军事动词，
   在记亭台对句的联话里完全错位
3. 同样造成嵌套

**留下的启发**：

> **不要因为"那边有"就移植。**
> 移植前必须问："这个类型在我的文体里对应什么实体？"
> 答不上来，就不该移植。

**这也回答了"本项目为什么没有动词层"**——不是忘了，是想清楚了。

### 5.3 第三次否决：信任"最近的实体"推断作者

**想法**：联前最近的人名十有八九是作者。

**为什么失败**：按作者分组统计后出现荒谬排名：

```
朱子 13 次 ← 集句联的"被集诗人"
王勃  8 次 ← "王勃东屋山池赋"是引文
紫阳  6 次 ← 多是"紫阳书院"这个地名
庄子  5 次 ← "庄子七言云"是集句
```

**修正**：高精度模式 + 两层过滤（见 SKILL_04 §9）。
覆盖率 8.4% → 3.0%，但准确率从"不可用"到"可用"。

**留下的启发**：

> **元数据宁可缺，不可错。**
> 空白时研究者会自己查；错了会直接引用错误结论。

### 5.4 三次否决的共同结构

| | 第一次 | 第二次 | 第三次 |
|---|---|---|---|
| 表面合理性 | 语法统一 | 复用成熟体系 | 规则极简、覆盖率高 |
| 失败原因 | 嵌套 | 语义错位 | 精度不足 |
| 发现方式 | 写完即检查 | 逐条检查 | **统计分布反常** |
| 修正方向 | 改前缀标记 | 不移植 | 提高精度、放弃召回 |

**共同点**：三次都是在"**看起来已经能用**"时被推翻的。

## 六、多轮反思的节奏

本项目的实际迭代（同一份数据，三轮）：

| 轮次 | 触发 | 发现 | 等长率 |
|---|---|---|---|
| 1 | 领域校验 | 末尾句读 | 1.4% → 93.7% |
| 2 | 剩余样本逐条看 | 出处冠名 | 93.7% → 99.1% |
| 3 | 剩余 28 副逐条看 | 冠名位置/长度 + 编者标记 | 99.1% → 99.34% |

**规律**：**每一轮都以为"差不多了"，下一轮又发现一层。**

> 第一轮的"基本对"往往只是"第一层对"。

**收敛判据**：不是"没有错误"，而是"**已知的错误模式都被处理过**"，
剩下的不确定性被**显式标注为不确定**，而不是伪装成确定。

## 七、禁止事项与推荐做法

### 7.1 禁止

❌ **只改这一处，不找同类** —— 同样的错误必然还会出现在别处。

❌ **批量替换式修正** —— "看起来像"的字眼必须逐个查证（Y10 的教训）。

❌ **按覆盖率优化** —— 覆盖率是虚荣指标，精度才是。

❌ **删掉不想要的字段而不留记录** —— 要写清"为什么删"（如 `balanced`）。

### 7.2 推荐

✅ **每次修正都问"还有多少同类"**。

✅ **把规律写进 SKILL**，而不是只写在 commit message 里。

✅ **保留反向规律**（Y10）—— 记录自己犯的错最有价值。

✅ **反思要写成可执行的检查** —— 而不是"下次注意"。

## 十、FAQ

**Q：规律库多长算太长？**
A：当前 11 条（Y0–Y10）。超过 30 条就该分组或合并——
规律太多说明设计有问题，而不是数据太复杂。

**Q：为什么不直接写测试，而写"规律"？**
A：两者互补。测试验证**已知行为**，规律指导**未知情况的判断**。
例如 Y1 无法写成测试（"哪些词与普通词同形"是开放集合），
但可以作为检查清单。

**Q：如何判断一条规律该不该进库？**
A：问"下一个 Agent 会不会重犯这个错？"
会 → 进库。只是本项目的偶发情况 → 记在 commit message 即可。
